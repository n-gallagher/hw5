Reflection

My take on how the agent team handled the three tickets in the graded run, using the ticket tabs and the Cash tab on this page as evidence.

Ticket 101: Bulldog tee

How the agents performed, and why

It performed well. The outcome was correct and safe: it didn't make a payment without my approval, it didn't promise a date, and nothing was sent to the customer. The main drawback was that it was less efficient than it needed to be. A straightforward, step-by-step ticket was split across four agents, which led to more model calls and repeated the same lookups.

Actual vs. my Expected plan

The run pretty closely matched the plan: Inventory went first, Facilities stayed out, the invoiced amount ($840) waited for my approval, and the draft didn't promise a date.

Some differences, though: the Boss sent all the tasks out at once instead of the Inventory → Accounting chain I expected, Customer Service asked Inventory to re-check, and the desk marked the ticket "resolved" while the payment was still waiting for me to approve it.

Would one agent with tools have been simpler?

One agent would likely have run the steps in one straight line with fewer model calls, because each step depends on the one before it and every tool is a quick lookup. Splitting the work across agents added repeated calls (the ticket, for example, was read 5 times), and context may have been lost between hand-offs. (Of the run's 19 model calls, the Boss used 4 to route the work, Accounting 4, Customer Service 4, and Inventory 7, because Inventory ran twice: once for the Boss and again when Customer Service asked it to re-check. That second pass repeated get_ticket, check_stock and check_vendor_hold for the same facts. The whole job needs about 8 tool calls (get_ticket, check_stock, list_vendors, check_vendor_hold, get_cash_position, request_payment, post_draft, update_ticket_status), so one agent doing them in order would be roughly 5–7 model calls, about a third of the 19 calls and ≈ $0.0081 cost, though that's an estimate.)

Evidence from this run (Ticket 101 tab · Cash tab): 19 model calls (Boss 4, Inventory 7, Accounting 4, Customer Service 4), 53,397 in / 5,516 out tokens, 4 hand-offs, ≈ $0.0081. get_ticket ×5, check_vendor_hold ×3, check_stock ×2. Request #1, invoice 501 for $840, was approved by Natty G: checking $3,400 → $2,560.

Ticket 102: Rent due

How the agents performed, and why

It performed well: the rent was filed but not paid, cash never went negative, and Accounting usefully advised paying the overdue invoice first, which left $160 once both were paid. So it was successful in the core functionality. On the downside, it was a bit wasteful, because a lookup-and-file ticket was split across two specialists who repeated each other's work.

Actual vs. my Expected plan

It closely matched the Expected plan: Facilities went first, only Facilities and Accounting were involved, and the rent was filed for approval. It differed in that the Boss called Accounting directly instead of Facilities handing off to it, and Accounting also checked invoice 501 so it could rank both bills. The desk again marked the ticket "resolved" while the payment was still pending, so it wasn't really resolved.

Would one agent with tools have been simpler?

This one was probably even more of a one-agent job than 101. In the log, Accounting re-ran Facilities' get_rent_due lookup itself, so Facilities added almost nothing it needed, and a single agent could have finished in fewer calls. (Of the run's 11 model calls, the Boss used 4 just to route the work and Facilities used 3, about 5,400 input tokens or ≈ $0.0008, for one lookup that Accounting then repeated. Accounting's own 4 calls covered every lookup the ticket needed: get_ticket, get_cash_position, get_today, get_rent_due, get_invoice, then request_payment. One agent doing that, plus a status update, would be roughly 4–5 calls and about half the ≈ $0.0046 cost, though that's an estimate.)

Ticket 103: Bulk hoodie discount

How the agents performed, and why

This one was the worst of the three, in my opinion. The run did stay safe: nothing was promised, approved or paid. But it reasoned pretty poorly. The escalation happened because the invoice was counted twice, and Accounting also answered with the greatest possible discount, which no one asked for. More agents means more hand-offs, and each hand-off lost context and repeated work.

Actual vs. my Expected plan

The run matched expectations pretty closely again: Inventory went first, Facilities wasn't called, the vendor hold blocked the restock (sad), Customer Service drafted without sending, and the ticket was escalated, which I thought it might be. But there were differences. Accounting never tried a restock order, so request_payment was never called. The Boss also got the cash wrong: it said the $160 left wasn't enough to cover invoice 501, but that $840 invoice was already counted as request #1 from ticket 101. So it wasn't accounting for things quite correctly.

Would one agent with tools have been simpler?

This one was probably the worst case for splitting the work. It took 26 calls: Inventory and Accounting each did their checks twice because Customer Service sent them the same questions the Boss had, and one hand-off loop had to be blocked. A single agent holding all the facts in one context wouldn't have had to re-ask anything, and it would likely have caught that the invoice was already pending (just a guess).

Evidence from this run (Ticket 103 tab · Cash tab): 26 model calls (Boss 5, Inventory 8 over 2 runs, Accounting 9 over 2 runs, Customer Service 4), 81,840 in / 9,431 out tokens, 5 hand-offs plus 1 blocked (Accounting → Boss), ≈ $0.0129, the most expensive ticket and the only one that moved no money ($0 on the Cash tab). get_ticket ×6, check_discount ×4, check_vendor_hold ×3. Where the cash error came from: Accounting's get_cash_position correctly listed both pending requests (#1 invoice 501 $840, #2 rent $2,400) and Accounting reported "$160 left after all requests". The Boss then read that $160 as still needing to cover the $840, double-counting it in the hand-off.

Three new problems this team could solve with the tools I built

  1. A morning status report. Report back on every open ticket and what's blocked. This would have the Boss work through the board and call whichever specialists each ticket needs, using tools already built: most likely list_open_tickets, get_ticket and update_ticket_status.
  2. A weekly bill check. Tell us what we owe, what's pending, and whether we can cover it all. This would call the Boss, who would call Accounting and Facilities, with the tools list_payment_requests, get_cash_position, get_invoice and get_rent_due.
  3. Restock the items at zero that I flag (like the size-small tee and the Crest Mug). As long as we have enough cash (cash can't go negative), we could restock with tools we already built. Inventory confirms the items are at zero with check_stock and finds the vendors with list_vendors and check_vendor_hold (Bulldog Print Co is no longer on hold now that invoice 501 is paid), and Accounting files two orders with request_payment, which wait for my approval.

Three new problems this team could not solve, and what it would need

  1. Find a backup vendor. Right now it can't find a backup vendor, so when we can't get an item in, it can't procure from a new source. It would need tools to search the web, get quotes and then add a vendor, so we'd need a new agent within this architecture, maybe a Procurement agent.
  2. Send repair requests to the landlord when something is broken at the shop or needs maintenance. We'd need to add tools to create maintenance requests and then work with the contractor to schedule service, so a schedule-service tool as well. That assumes the landlord finds the contractor; if we also have to find the contractor and then take it out of rent or something, we'd need a find-contractor tool as well. This could fit within the Facilities agent, but with more tools added in.
  3. Take payment or issue a refund for an order. This could really automate things. We'd need tools to create the order, charge the customer and issue the refund. This would probably need to be a new agent, like a Sales agent, and refunds will need human approval.

Why today's app can't do these (from this build): (1) vendors has only one apparel vendor, Bulldog Print Co, which is why tickets 101 and 103 both stalled on its invoice-501 hold, and no tool can add a vendor or search beyond the database (list_vendors only reads the 3 rows). (2) There is no maintenance table or tool; Facilities can only read the lease (get_rent_due), and shop rule 8 bars contacting the landlord, so any request would need to go out as a draft for a human. (3) Shop rule 7 says cash only goes out: no tool can add money to cash_accounts, which is why the Cash tab only ever shows decreases ($3,400 → $160), and customer orders like 101 and 103 never bring revenue in.
